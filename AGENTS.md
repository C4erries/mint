# AGENTS.md

## Назначение

Этот документ фиксирует обязательные инженерные правила для репозитория **Mint**. Правила ниже считаются базовыми и должны соблюдаться во всех новых пакетах, сервисах, тестах и инфраструктурных изменениях.

## Технологическая рамка

- Репозиторий: **monorepo**.
- Язык backend: **Go**.
- Точки входа: отдельные бинарники в `cmd/<service>/main.go`.
- Архитектурный стиль: **DDD + CQRS**.
- Синхронное взаимодействие между backend-сервисами: **gRPC**.
- Внешний API для desktop frontend: **REST через core-api**.
- Write-path: **через Kafka**.
- Read-path: **напрямую через query/read model**, без Kafka в запросном пути.
- Для гарантированной доставки событий там, где это нужно, используем **outbox pattern**.
- Логирование: **slog**.
- Тестовый стек: **testing + testify + mockery**.
- Локальный запуск: **Docker + docker-compose**.
- RTC/media: **LiveKit**.
- Хранилища: в зависимости от контекста — **ScyllaDB**, **Redis**, object storage и интеграции с внешними системами.

## Общие архитектурные правила

### 1. Monorepo и структура проекта

- Репозиторий содержит несколько сервисов/бинарников.
- Каждая точка входа — отдельный `main.go` в `cmd/<service>/`.
- `main.go` является **composition root**: там собираются зависимости, конфиг, логгер, transport, consumers, background jobs.
- Доменные модули лежат в `internal/<bounded_context>/...`.
- Общие пакеты в `pkg/` допускаются только для реально общих и технически нейтральных компонентов. Нельзя выносить в `pkg/` бизнес-логику “потому что переиспользуется”.

Рекомендуемая форма:

### 2. DDD: обязательное разделение на слои

#### Domain

`domain/` — чистая предметная область.

В `domain` допустимы:
- сущности,
- value objects,
- aggregate roots,
- доменные сервисы,
- доменные ошибки,
- доменные события,
- бизнес-инварианты и правила.

В `domain` **недопустимы**:
- JSON/YAML/DB теги,
- зависимости на Kafka, Redis, Scylla, LiveKit, HTTP/gRPC,
- `context.Context`,
- логгеры,
- DTO транспортного слоя,
- ORM/driver-модели,
- технические ID/response-модели внешних SDK, если они не являются частью предметной области.

Домен не должен знать, как он хранится, сериализуется, логируется и по какому транспорту вызывается.

#### Application

`application/` — слой use case’ов и orchestration.

В `application` располагаются:
- command handlers,
- query handlers,
- application services,
- координация репозиториев, транзакций, idempotency и policy checks,
- DTO команд/запросов/ответов,
- orchestration вокруг outbox, event publication, integration calls.

`application` знает про интерфейсы репозиториев и адаптеров, но не про конкретную техническую реализацию.

#### Infrastructure

`infrastructure/` — адаптеры и интеграции.

Здесь находятся адаптеры с обязательным разделением на входящие и исходящие:
- `in/`: REST handlers (внешний frontend-вход в `core-api`), gRPC servers, Kafka consumers, webhook handlers;
- `out/`: реализации репозиториев, Kafka producers, gRPC clients, LiveKit clients, Redis/Scylla/object storage adapters, клиенты внешних систем;
- `di/container.go`: сборка dependency graph инфраструктурного слоя (конструкторы адаптеров/сервисов), чтобы `main.go` оставался тонким и чистым;
- transport DTO mapping и преобразование моделей на границах адаптеров.

### 3. CQRS: фиксированные правила

- **Команды и записи** идут через **Kafka**.
- **Чтение** идёт **напрямую** в query/read model, без Kafka в синхронном запросном пути.
- Desktop frontend ходит по REST только в `core-api`.
- Синхронные межсервисные вызовы выполняются только по gRPC.
- Команда не должна изменять состояние напрямую из HTTP/gRPC handler’а. Handler валидирует минимум, публикует команду, возвращает подтверждение принятия и correlation/command id.
- Изменение write model выполняет command consumer / application handler на write-side.
- Query-side не должен тащить в себя write-side зависимости без веской причины.
- Read model разрешено денормализовать под UI и конкретные query use cases.
- Eventual consistency между write и read частью считается нормой и должна быть отражена в API/UX.

Практический минимум:
- команды именуются в повелительном наклонении: `CreateWorkspace`, `SendMessage`, `JoinVoiceChannel`;
- доменные события именуются в прошедшем времени: `WorkspaceCreated`, `MessageSent`, `VoiceChannelJoined`.

### 4. Kafka: правила работы

- Partition key выбираем так, чтобы сохранять порядок в рамках агрегата (`workspace_id`, `channel_id`, `conversation_id`, `message_id`, `room_id` и т.п.).
- Все consumers должны быть **idempotent**.
- Сообщения должны иметь correlation id / causation id / command id, если это уместно по сценарию.
- Нельзя полагаться на “exactly once” как на магию инфраструктуры. Логика должна быть устойчива к повторной доставке.
- Повторная обработка команды или события не должна приводить к дублированию состояния.

### 5. Outbox: обязательные правила

Outbox используется там, где после изменения состояния мы обязаны надежно опубликовать событие или интеграционное сообщение.

Обязательные правила:
- нельзя делать схему “сначала записали состояние, потом best effort отправили в Kafka”;
- если изменение состояния обязано породить событие — используем outbox;
- outbox relay может жить как background loop внутри сервиса или как отдельный worker, но гарантия доставки должна быть сохранена;
- если основное хранилище плохо подходит для наивной transactional outbox-схемы, нужно проектировать write model и outbox так, чтобы не терять события: одна partition/единица атомарности, LWT/conditional write, append-only log либо отдельное транзакционное решение для outbox. Best effort publish после успешной записи запрещён.

### 6. Интерфейсы: располагать по месту использования

- Интерфейсы объявляются **там, где они нужны**, а не там, где реализуются.
- Если use case использует репозиторий или gateway — интерфейс живет рядом с use case/application layer.
- Не создавать “папку interfaces” или центральный god-package с интерфейсами.
- Конкретная реализация должна зависеть от интерфейса, определённого у потребителя.

### 7. DI и clean code

- Используем явный **constructor injection**.
- Никаких service locator, package-level singleton, скрытых глобальных зависимостей.
- Конфиг собирается централизованно в composition root.
- Пакеты должны быть маленькими и сфокусированными.
- У каждого публичного типа и метода должна быть чёткая ответственность.
- Предпочитаем явные зависимости и простые конструкторы.
- Не допускается смешение domain logic с transport/infrastructure details.
- Допускается разделение application на `command/` и `query/`, если это улучшает читаемость.

### 8. Логирование

- Используем только **slog**.
- Логи структурированные.
- В логах должны быть поля контекста, когда это уместно: `request_id`, `trace_id`, `command_id`, `user_id`, `workspace_id`, `channel_id`, `conversation_id`, `message_id`, `room_id`.
- Не логировать бизнес-события из `domain/`.
- Не проглатывать ошибки.
- При возврате ошибки — либо оборачивать её с контекстом, либо переводить в явную доменную/application ошибку.

### 9. Обработка ошибок

- **Ошибки не игнорируем.**
- Запрещено использовать `_ = err` и аналогичные паттерны для сокрытия ошибки.
- Ошибки должны быть проверены, обработаны или возвращены наверх.
- Нельзя чинить логику за счёт подавления ошибки в тестах или прод-коде.
- `panic` допустим только для truly unrecoverable startup/configuration проблем в `main` или узком техслое; в бизнес-потоке не используем.

### 10. Тестирование

Обязательные правила для unit tests:
- использовать **табличные тесты**;
- использовать `t.Run(...)`;
- использовать `t.Parallel()` там, где тест действительно потокобезопасен и независим;
- использовать **testify** для assert/require;
- моки генерировать через **mockery** и конфигурацию в `mockery.yml`;
- **ошибки в тестах не игнорировать**;
- если функция возвращает `err`, тест обязан его явно проверять;
- для негативных сценариев проверять тип/семантику ошибки, а не только факт её наличия.

Обязательные правила для исправления багов:
- если упали blackbox/e2e тесты и проблема действительно в коде — исправляем код, а не “подгоняем” тест;
- если нашли логическую ошибку — добавляем **регрессионный тест**;
- тест меняем вместо кода только если ошибка реально в логике теста или устарела спецификация.

Рекомендуемая градация:
- unit tests — бизнес-логика и application handlers;
- integration tests — репозитории, Kafka adapters, Redis/Scylla integrations, outbox relay;
- blackbox/e2e — сценарии поверх сервисов целиком.

### 11. Маппинг и DTO

- DTO транспортного слоя не проходят в домен.
- Маппинг `transport -> application input`, `domain -> query DTO`, `infrastructure model -> domain` делается явно.
- Не использовать domain entities как JSON response model.
- Не добавлять теги сериализации в domain structs.

### 12. Репозитории и модели хранения

- Репозитории работают с доменными агрегатами или явно обозначенными query projections.
- Модели Scylla/Redis/SQL/object storage не должны утекать в domain.
- Query-side может использовать отдельные projection-модели, оптимизированные под чтение.

### 13. Политика зависимостей

- Используем только стабильные релизы библиотек (без alpha/beta/rc/pre-release) для production-контура.
- Версии зависимостей фиксируем явно в `go.mod`/`go.sum`; плавающие диапазоны не допускаются.
- При добавлении или обновлении зависимостей проверяем актуальную стабильную версию по официальным релиз-источникам.
- После изменения зависимостей обязательно прогоняем линтеры и тесты.

### 14. Docker и локальный запуск

- Каждый сервис должен иметь понятный Dockerfile или включаться в общий build pipeline.
- Для локальной разработки обязателен `docker-compose`.
- Compose должен поднимать минимальный рабочий набор: Kafka, Redis, Scylla, LiveKit/RTC-зависимости, object storage, сами сервисы по необходимости.
- Локальный сценарий старта должен быть воспроизводимым одной командой или короткой последовательностью команд.

### 15. Критерии “сделано хорошо”

Код считается приемлемым, если:
- соблюдена слоистая архитектура,
- домен остаётся чистым,
- внешний frontend работает через REST `core-api`, а межсервисные синхронные вызовы идут по gRPC,
- write-path идёт через Kafka,
- read-path не завязан на Kafka,
- infrastructure разделена на `in/out` адаптеры,
- outbox применён там, где потеря события недопустима,
- зависимости зафиксированы на стабильных версиях,
- ошибки не игнорируются,
- тесты табличные и осмысленные,
- логика исправляется в коде, а не маскируется тестом,
- DI явный,
- интерфейсы лежат у потребителя,
- код остаётся читаемым и поддерживаемым.
