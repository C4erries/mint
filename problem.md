# problem.md

## Название проекта

**Mint**

## Что это за проект

Mint — self-hosted / локально управляемое desktop-приложение для общения, которое объединяет две продуктовые линии:

- удобство и структуру **Discord-подобных** пространств: серверы/workspaces, каналы, роли, voice/video комнаты;
- простоту и прямолинейность **Telegram-подобного** общения: личные диалоги, быстрые чаты, привычный messaging flow.

На текущем этапе это **pet-проект с прицелом на локальное использование и постепенное развитие**, а не попытка сразу строить публичную платформу масштаба Discord/Telegram.

## Зачем проект нужен

Основная идея — получить единое desktop-приложение, в котором можно:

- вести личные диалоги и групповые переписки;
- иметь серверы/workspaces с каналами и ролями;
- использовать voice/video комнаты;
- хранить и пересылать вложения;
- видеть presence, typing, unread counters и прочие базовые realtime-сигналы;
- позже подключать интеграции и мосты, в том числе Telegram-like / external chat workflows.

Проект должен оставаться инженерно чистым и удобным для развития, а не превращаться в набор хаотичных хендлеров и таблиц.

## Основная продуктовая картина

Mint — это desktop-first коммуникационное приложение, где пользователь может:

1. завести аккаунт и открыть приложение;
2. настроить профиль;
3. создавать или использовать workspaces/servers;
4. общаться в каналах и личных диалогах;
5. подключаться к голосовым и видеокомнатам;
6. видеть, кто онлайн, кто печатает и кто находится в voice room;
7. получать локальные/in-app уведомления;
8. в будущем использовать внешние интеграции и мосты.

## Основные сценарии

### 1. Аккаунт и сессии
Пользователь может войти в приложение, управлять своими сессиями и безопасно продолжать работу между запусками desktop-клиента.

### 2. Профиль и социальная модель
Пользователь имеет display name, avatar, настройки приватности, список отношений с другими пользователями и блокировки.

### 3. Workspace / Server модель
Пользователь может создавать пространства, каналы, приглашать участников, управлять ролями и правами доступа.

### 4. Сообщения
Пользователь может:
- писать сообщения в каналах;
- вести direct messages;
- редактировать и удалять свои сообщения;
- ставить реакции;
- работать с history и unread/read markers.

### 5. Voice / Video
Пользователь может подключаться к voice/video комнатам, выключать микрофон и камеру, видеть состав комнаты и получать понятное состояние подключения.

Для media-слоя используется **LiveKit**. Сам проект не реализует свой WebRTC SFU на старте.

### 6. Realtime
Пользователь видит:
- online/offline/idle состояния,
- typing indicators,
- изменения состава каналов и комнат,
- доставку новых сообщений и события вокруг них.

### 7. Вложения и медиа
Пользователь может загружать файлы, прикреплять их к сообщениям, открывать превью и хранить ссылки на медиаобъекты.

### 8. Уведомления
Пользователь получает in-app/unread/mention-сигналы, достаточные для комфортной работы в desktop-клиенте.

## Что важно для проекта

### Не делать чрезмерное дробление
Проект не должен быть раздроблен на десятки микросервисов. Предпочтение отдаётся умеренному разбиению на крупные логические зоны ответственности.

### Сохранять чистую архитектуру
Система должна строиться вокруг предметной области, а не вокруг инфраструктуры. Транспорт, хранилища, кэш, Kafka и LiveKit не должны диктовать доменную модель.

### Заложить развитие вперёд
Даже как pet-проект, Mint должен иметь архитектурную основу, позволяющую:
- добавлять новые фичи без переписывания ядра;
- подключать интеграции;
- масштабировать наиболее нагруженные части отдельно;
- не терять события и не ломать consistency-поток.

## Базовое техническое направление

- Backend: **Go**
- Архитектура: **DDD + CQRS**
- Write-path: **через Kafka**
- Read-path: **напрямую**
- Надежная публикация событий: **outbox pattern**, где это необходимо
- RTC/media: **LiveKit**
- Realtime/ephemeral state: **Redis**
- Durable/query storage: **ScyllaDB**
- Desktop client: **React + Electron**
- Логирование: **slog**
- Локальная инфраструктура: **Docker + docker-compose**

## Логическая серверная разбивка без перегиба

На текущем этапе проект логически делится на несколько крупных зон:

- identity / auth,
- profile / social,
- workspace / channels / permissions,
- messaging,
- realtime / presence,
- rtc / voice-video orchestration,
- media / attachments,
- notifications,
- integrations (позже, по мере необходимости).

Физически это может быть собрано как несколько бинарников в одном monorepo, без излишней микросервисной фрагментации.

## Что не является целью ближайшего этапа

На ближайшей стадии проект **не обязан**:
- конкурировать по масштабу с Discord/Telegram;
- поддерживать огромные публичные сообщества;
- иметь сложную мультирегиональность;
- реализовывать собственный media server вместо LiveKit;
- покрывать все возможные интеграции сразу;
- делать мобильные клиенты раньше стабильного desktop experience.

## Критерий успеха ближайшей версии

Можно считать, что направление выбрано правильно, если получается self-hosted desktop-приложение, где:

- пользователь входит в систему без боли;
- есть workspaces, каналы и direct messages;
- сообщения и вложения работают стабильно;
- presence и realtime ощущаются живыми;
- voice/video комнаты работают через LiveKit;
- архитектура остаётся чистой и не мешает развитию.
